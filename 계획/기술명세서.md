# KNU Campus Life 기술명세서

## 1. 시스템 개요

KNU Campus Life는 강남대학교 학생을 위한 통합 캠퍼스 앱이다. 백엔드는 FastAPI 기반 REST API로 인증, 공지사항, 식단, 셔틀 시간표, 강의/과목, 시간표, 개인 일정, 챗봇, **푸시 알림**, **첫 수업 기반 등교시간 역산 및 지도 안내** 기능을 제공한다. 프론트엔드는 React Native Expo 기반 모바일 앱으로 구성한다. 현재 배포 기준은 **Google Cloud Run + Supabase PostgreSQL + Qdrant Cloud + Cloudflare Workers AI**이며, Oracle 배포 구성은 폐기되었다. 통학 경로는 Google Routes API를 사용하고, 지도 화면은 `expo-maps` 기반으로 전환 중이며 Android 우선 지원을 기준으로 한다.

### 1.1 최종 운영·정책 기준 (2026-11-03)

- 서비스 대상은 강남대학교 학생으로 제한한다. 학생 여부는 학교 이메일 일회용 코드(OTP)로 확인한다.
- 회원가입 시 학생 인증이 완료되기 전에는 일반 서비스 권한을 부여하지 않는다. 인증 대기 상태에서는 인증·계정 설정 API만 허용한다.
- Google 로그인 성공 후에도 즉시 정식 토큰을 발급하지 않고, 학생 이메일 인증을 완료한 뒤 정식 세션을 발급한다.
- 동일 이메일의 기존 계정과 Google 계정을 자동 연결하지 않는다. 사용자가 기존 계정으로 로그인한 뒤 별도의 계정 연결 절차를 완료해야 한다.
- 통학용 학교 포털 학번·비밀번호를 일반 사용자에게 요구하거나 저장하지 않는다. 크롤링이 필요한 경우 관리자/서비스 계정을 Secret Manager로 관리한다.
- 인증 토큰은 access/refresh 용도를 `type` 클레임으로 구분한다. refresh 요청은 `refresh_sessions`의 `session_id`, 해시된 `jti`, 사용자 상태 및 `token_version`을 검증하고 성공 시 refresh token을 회전한다.
- 비밀값은 Cloud Run 환경변수에 직접 기록하지 않고 Google Secret Manager에서 주입한다. `SECRET_KEY`의 코드 내 fallback은 배포 전 제거해야 한다.
- Oracle VM, Oracle용 Docker/환경/백업 문서는 삭제했으며 Cloud Run 배포 문서만 정본으로 유지한다.

| GET | `/api/commute/realtime-bus` | 개발 예정 | 선택 버스 구간의 최신 도착정보, 남은 정류장 및 지원 시 차량 위치 반환 |
| GET | `/api/maps/walking-route` | 개발 예정 | 현재 위치에서 선택한 교내 건물까지 Google 보행 경로 반환 |

## 4. 주요 구현 구조

### 4.1 인증 및 권한

- 이메일/비밀번호 회원가입은 학생 이메일 OTP 인증을 완료한 경우에만 정식 계정으로 활성화한다.
- Google 로그인은 학생 인증 대기 상태를 거친 뒤 정식 access/refresh token을 발급한다.
- `/auth/refresh`는 access token 의존성 없이 refresh token의 `type`, 서명, 만료, `session_id`, 해시된 `jti`, 사용자 상태 및 `token_version`을 검증하고 성공 시 두 토큰을 회전한다.
- `/auth/logout`은 현재 refresh 세션을 폐기한다.
- `/auth/me`는 현재 사용자 정보와 `is_admin` 값을 반환한다.
- 사용자 정보 수정 및 알림 설정 API가 구현되어 있다.

### 4.2 공지사항

- 개선된 `notice_crawler_v3`를 통해 본문 내 이미지까지 수집한다.
- 새 공지 수집 시 **해당 카테고리 알림을 허용한 사용자들에게 푸시 알림을 즉시 발송**한다.
- 공지사항 목록은 무한 스크롤 및 카테고리 필터를 지원한다.

### 4.3 식단

- 주간 식단표 이미지를 크롤링하여 날짜별로 저장한다.
- 새로운 식단표가 업데이트되면 **알림 허용 사용자들에게 푸시 알림을 발송**한다.

### 4.4 셔틀 시간표

- 최신 셔틀 시간표 PDF 링크를 수집하고 RAG 문서로 인덱싱한다.
- 새 시간표 등록 시 **푸시 알림을 발송**한다.

### 4.5 RAG 챗봇 및 채팅방 관리

- **채팅방 관리**: 채팅방 생성, 삭제, 이름 수정 기능이 구현되어 있으며, Drawer 메뉴에서 Long Press로 설정 모달을 띄울 수 있다.
- **자동 제목 생성**: 새 채팅방에서 첫 질문을 던지면 질문 내용의 앞부분을 따서 채팅방 제목을 자동으로 설정한다.
- **Empty State**: 채팅 메시지가 없을 때 추천 질문을 제안하여 대화를 유도한다.
- 공지사항, 셔틀, 학사일정, 학교 규정 데이터를 기반으로 답변한다.

### 4.6 푸시 알림 (Push Notification)

- **Backend**: Expo Push API를 사용하여 `NotificationSetting` 테이블에 저장된 토큰으로 알림을 전송한다. 크롤러 작업 완료 시 `notify_users_by_type` 함수를 호출한다.
- **Frontend**: 앱 실행 시 `expo-notifications`를 통해 권한을 요청하고 토큰을 획득하여 서버에 등록한다. 알림 클릭 시 해당 화면으로 이동하는 로직을 갖춘다.

### 4.7 Scheduler

- APScheduler를 통해 공지사항(1시간), 학식(매일 새벽 1시), 셔틀(12시간) 크롤링을 정기적으로 수행한다.

### 4.8 친구 시스템 및 시간표 공유 구조 (Friendship & Timetable Sharing)

- **상태 관리**: `PENDING`(요청 대기), `ACCEPTED`(친구 완료), `REJECTED`(거절)의 3가지 상태로 관리되며, 요청자-수신자 간 유니크 인덱스를 통해 중복 요청을 방지한다.
- **프라이버시 보호**: 시간표 열람 API 호출 시 요청자와 대상 사용자의 친구 관계(`ACCEPTED`)를 반드시 검증하며, 비인가 접근 시 403 Forbidden을 반환한다.
- **프론트엔드 UI**: 시간표 화면 상단 [친구] 버튼을 통해 친구 모달 진입, 친구 목록에서 탭 시 내 시간표와 동일한 포맷의 전용 주간 그리드 뷰어로 친구 시간표를 렌더링한다.

### 4.9 1:1 쪽지(메시지) 구조 (Direct Messaging)

- **대화 내역 관리**: 발신자/수신자 ID와 메시지 본문, 수신일시 및 `is_read` 플래그를 저장한다.
- **방 목록 집계**: `GROUP BY` 또는 최신 메시지 서브쿼리를 활용하여 대화 상대별 최신 대화 1건과 읽지 않은 메시지 개수를 계산하여 효율적으로 반환한다.

### 4.10 에브리타임 스타일 커뮤니티 구조 (Community)

- **익명성 보장**: `is_anonymous` 플래그를 두며, 익명 작성 시 작성자 고유 식별자는 감추고 "익명" 또는 게시글 내 댓글 순번(예: 익명1, 익명2, 작성자)으로 표시한다.
- **좋아요 중복 방지**: `post_likes` 테이블에 `user_id`와 `post_id`를 복합 유니크 키로 두어 1인 1회 추천만 가능하도록 보장한다.

### 4.11 Google 기반 등교시간 역산 및 통합 지도 구조

#### 4.11.1 서비스 분리

- `app/services/commute.py`: 통학 프로필, 첫 수업, 셔틀 시간표와 외부 경로 결과를 조합하는 도메인 오케스트레이션을 담당한다.
- `app/services/google_routes.py`(신규): Google Routes 요청 생성, 응답 검증, polyline·구간·대중교통 상세 변환과 Google 오류 처리를 담당한다.
- `app/services/public_transit.py`(신규): TAGO 정류장·노선 매칭, 실시간 도착정보 및 차량 위치 조회를 담당한다.
- 외부 API의 원본 응답을 프론트엔드에 그대로 전달하지 않고 Pydantic 응답 모델로 정규화한다.

#### 4.11.2 첫 수업 및 목표 도착시각 계산

1. 사용자의 `CommuteProfile`을 조회한다.
2. 대표 시간표를 우선 선택하고, 없으면 최신 시간표를 선택한다.
3. Asia/Seoul 기준 오늘 수업 중 시작시각이 가장 빠른 수업을 선택한다.
4. `목표 도착시각 = 첫 수업 시작시각 - departure_buffer_minutes`로 계산한다.
5. 첫 수업 전이면 목표 도착시각을 Google Routes API의 `arrivalTime`으로 전달한다.
6. Google이 반환한 실제 `departureTime`을 홈 화면의 추천 출발시각으로 사용한다.
7. 첫 수업이 이미 시작되었으면 현재 시각 기준 경로를 조회하고 예상 이동시간만 제공한다.

기존 방식처럼 현재 경로의 평균 소요시간을 수업시각에서 단순 차감하지 않고, 목표 도착시각에 이용할 수 있는 대중교통 운행편 자체를 검색한다.

#### 4.11.3 Google Routes 응답 정규화

Google Routes API에는 필요한 필드만 Field Mask로 요청한다.

```text
routes.duration
routes.distanceMeters
routes.polyline.encodedPolyline
routes.legs.steps.travelMode
routes.legs.steps.duration
routes.legs.steps.polyline.encodedPolyline
routes.legs.steps.navigationInstruction
routes.legs.steps.startLocation
routes.legs.steps.endLocation
routes.legs.steps.transitDetails
```

응답은 다음 내부 구조로 변환한다.

```text
CommuteTodayResponse
└── recommended_route: RouteSummaryResponse
    ├── departure_time / arrival_time
    ├── duration_minutes / walking_minutes / transfer_count
    ├── encoded_polyline
    ├── steps[]
    │   ├── travel_mode
    │   ├── instruction
    │   ├── encoded_polyline
    │   └── transit_details
    │       ├── vehicle_type / line_name
    │       ├── departure_stop / arrival_stop
    │       └── departure_time / arrival_time
    └── realtime_bus
```

- Google의 초 단위 duration은 올림하여 분 단위 정수로 변환한다.
- RFC3339 시각은 Asia/Seoul 기준으로 변환한 뒤 프론트엔드에 ISO 형식으로 전달한다.
- `BUS`, `SUBWAY`, `TRAIN`, `LIGHT_RAIL` 등 구간을 현재 `transport_type` 계약에 맞게 정규화한다.
- 전체 polyline과 구간별 polyline을 함께 반환하여 지도 스타일을 구간별로 다르게 적용할 수 있도록 한다.

#### 4.11.4 교내 셔틀 역산

1. 첫 수업 목표 도착시각 이전에 이공관에 도착하는 셔틀 후보를 조회한다.
2. 이용 가능한 후보 중 가장 늦게 출발하는 셔틀을 선택한다.
3. `셔틀 탑승 목표시각 = 기흥역 셔틀 출발시각 - 탑승 여유시간`을 계산한다.
4. 집에서 기흥역까지 Google 대중교통 경로를 `arrivalTime` 기준으로 조회한다.
5. Google 대중교통 구간, 셔틀 대기시간, 셔틀 운행시간을 합산하여 최종 출발시각과 총 소요시간을 반환한다.

#### 4.11.5 TAGO 실시간 버스 결합

1. Google 버스 단계에서 노선번호, 승차 정류장명과 좌표를 추출한다.
2. 좌표와 정류장명으로 가장 가까운 TAGO 정류장의 `cityCode`와 `nodeId`를 찾는다.
3. 정류장을 통과하는 노선 중 Google 노선번호와 일치하는 `routeId`를 선택한다.
4. 버스도착정보 API로 도착 예정시간과 남은 정류장 수를 조회한다.
5. 버스위치정보 API로 해당 노선 차량들의 WGS84 GPS 좌표를 조회한다.
6. 실시간 정보 조회가 실패하면 해당 필드만 `null`로 처리하고 Google 기본 경로는 정상 반환한다.

노선번호만 같은 반대 방향 버스를 선택하지 않도록 승차 정류장과 노선 방향을 함께 검증한다. 지원 지역 차이로 매칭되지 않는 노선은 Google 예정 출발시각으로 대체한다.

#### 4.11.6 단일 Google 지도 화면 상태 관리

`campus-map.tsx`는 별도의 `campus`/`commute` 라우트 모드로 분리하지 않고 하나의 화면과 지도 인스턴스를 유지한다.

```text
기본 캠퍼스 상태
├── 캠퍼스 건물·편의시설 표시
├── 건물 검색 및 교내 보행 경로
└── [등교 길안내] 버튼
          ↓
등교 안내 활성 상태
├── Google 대중교통 경로선
├── 승하차 정류장과 단계별 안내
├── 사용자 및 실시간 버스 위치
└── [안내 종료] 버튼
          ↓
기본 캠퍼스 상태로 복귀
```

- 지도 내부 상태는 `guidanceActive`로 관리한다.
- 지도 탭에서 일반 진입한 사용자는 `등교 길안내` 버튼으로 안내를 시작한다.
- 홈 `CampusRouteCard`의 `경로보기`는 같은 화면으로 이동한 뒤 안내 시작 동작을 전달한다. 이는 별도 화면 모드가 아니라 최초 한 번 실행할 UI 동작이다.
- 안내 종료 시 경로선, 정류장·차량 마커, 안내 패널과 실시간 폴링을 제거하되 캠퍼스 건물 마커는 유지한다.
- 지도 SDK와 React Native 상태를 직접 연결하며, 기존 WebView 메시지 브리지는 사용하지 않는다.

```text
INITIALIZE_MAP
CENTER_MAP
DRAW_TRANSIT_ROUTE
DRAW_WALKING_ROUTE
UPDATE_USER_LOCATION
UPDATE_BUS_LOCATIONS
SELECT_ROUTE_STEP
CLEAR_ROUTE
```

#### 4.11.7 프론트엔드 데이터 흐름

- `CampusRouteCard`와 `campus-map.tsx`는 TanStack Query의 `['commute', 'today']` 캐시를 공유한다.
- 홈에서 계산한 경로가 유효하면 지도 화면에서 재사용하고, 데이터가 없거나 만료되었으면 `/api/commute/today`를 다시 조회한다.
- 큰 polyline과 단계 배열은 라우트 파라미터로 전달하지 않는다.
- 실시간 버스 정보는 안내가 활성화되고 앱이 포그라운드일 때만 20~30초 주기로 갱신한다.
- Google 경로 재계산과 버스 위치 갱신을 분리하여 Routes API를 불필요하게 반복 호출하지 않는다.

#### 4.11.8 지도 표시 규칙과 키 보안

- Google Routes 경로는 Google 지도 SDK가 제공하는 지도 위에만 표시한다.
- Google 기본 출처 표시는 숨기거나 가리지 않으며 TAGO 정보에는 공공데이터 출처를 별도로 표시한다.
- Routes API 키는 백엔드 환경변수로만 관리하고 앱 번들에 포함하지 않는다.
- Android 지도 키는 패키지명·SHA-1 등 앱 제한을 적용하고, 서버 Routes 키와 분리한다.
- 현재 위치는 경로 계산과 화면 표시 용도로만 사용하고 기본적으로 DB에 저장하지 않는다.

### 5.1 Google 통합 지도 기능 검증 예정 항목

- `arrivalTime`이 첫 수업 시작시각에서 여유시간을 뺀 값과 일치하는지 검증
- Google 응답의 duration, RFC3339 시각, polyline 및 대중교통 단계를 내부 모델로 정확히 변환하는지 검증
- 첫 수업 없음, 프로필 없음, 건물 좌표 없음, Google 경로 없음과 API 장애 상태를 구분하는지 검증
- 버스 노선번호·승차 정류장·방향을 이용한 TAGO 노선 매칭 검증
- TAGO 장애 시에도 Google 기본 경로가 유지되는지 검증
- 지도 탭에서 버튼으로 안내 시작·종료가 가능하고 홈 카드 진입 시 동일 안내가 자동 시작되는지 검증
- 안내 종료·화면 이탈·백그라운드 전환 시 실시간 폴링이 중단되는지 검증
- Android 실기기에서 지도 키 제한과 렌더링 동작 검증; iOS는 지원 범위를 별도로 고지

## 6. 단계별 개발 로드맵

- **Phase 1: 친구 시스템 및 친구 시간표 공유 기능** (현재 진행 중)
  - DB 모델 `Friendship` 설계 및 Alembic/Base 마이그레이션
  - 친구 검색, 요청, 수락/거절/취소, 목록, 삭제 API 구현
  - 친구 시간표 조회 API (`GET /api/friends/{friend_id}/timetable`) 구현
  - 프론트엔드 친구 관리 모달 및 친구 시간표 그리드 뷰어 컴포넌트 개발
- **Phase 2: 1:1 쪽지(메시지) 시스템**
  - DB 모델 `DirectMessage` 설계
  - 대화 목록, 대화 상세, 메시지 전송 및 읽음 처리 API 구현
  - 쪽지함 및 실시간/폴링 대화 UI 개발
- **Phase 3: 커뮤니티 및 게시판 시스템**
  - DB 모델 `Board`, `Post`, `Comment`, `PostLike` 설계
  - 게시판/게시글/댓글 CRUD 및 익명 처리, 좋아요 API 구현
  - 게시판 목록, 글 상세, 작성/수정, 댓글 UI 개발
- **Phase 4: Google 기반 등교시간 역산 및 통합 지도 안내**
  - `google_routes.py`, `public_transit.py` 서비스 분리
  - Google Routes `arrivalTime` 기반 일반 등교 및 셔틀 역산 구현
  - 상세 경로·polyline·대중교통 단계 응답 스키마 확장
  - `campus-map.tsx`의 기존 지도 구현을 `expo-maps` 기반으로 정리
  - 단일 지도 화면의 `등교 길안내` 시작·종료 상태 구현
  - 홈 `CampusRouteCard`에서 동일한 지도 안내를 즉시 시작하도록 연결
  - TAGO 실시간 버스 도착정보 및 차량 위치 연동
  - 단위·통합·실기기 테스트와 API 호출량 최적화
- **Phase 5: 부가 고도화 과제**
  - Google 로그인 백엔드 로직 검증 및 보완
  - 공지사항 읽음 상태 API 구현
  - 졸업 요건, 기이수 과목, 위저드 선택 관련 실제 데이터 연동
  - 관리자 전용 데이터 관리 대시보드 UI
